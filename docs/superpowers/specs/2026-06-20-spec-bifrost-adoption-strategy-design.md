# Spec Bifrost 首批用户验证与推广策略

## 背景

Spec Bifrost v0.4.1 已具备从自然语言需求到本地 `spec-bifrost.json`、校验、预览和前后端需求文档导出的完整 MVP 链路，并支持 Claude Code、Codex 和 OpenCode。当前工程状态稳定，自动化检查已覆盖核心校验、hook、renderer、CLI、插件配置和示例。

现阶段最大的不确定性不是技术可行性或组件数量，而是外部团队是否认可并实际使用这条工作流。公开仓库尚未出现能够验证产品价值的外部使用反馈。继续扩展 schema、renderer 或组件能力会增加闭门造车风险。

因此，下一阶段从功能建设转为推广验证：在获得有效外部反馈前冻结产品代码，通过现有 v0.4.1 和采购系统示例验证目标用户、核心问题与协作价值。

## 目标用户

目标用户不是单一岗位，而是从零建设 B 端系统的企业产品研发团队，包括小公司和大公司。

这些团队具备以下特征：

- 产品和开发都已在各自工作中使用 AI。
- 产品侧与开发侧的 AI 上下文没有联通，需求需要重复转述。
- 团队不会完全信任 AI 直接生成的生产代码。
- 团队需要一种可审查、可校验、可版本化的需求资产连接产品与开发。
- 产品与开发愿意共同参与试用，而不是由某个岗位单独完成全部流程。

首批验证场景聚焦从零规划新的 B 端系统，不优先覆盖已有系统迭代或既有 PRD 迁移。

## 核心价值假设

Spec Bifrost 的核心价值不是更快生成原型，而是让产品与开发围绕同一份结构化需求资产协作，减少重复转述和语义漂移。

目标工作流是：

1. 产品通过 AI 描述业务目标、页面、流程、规则和边界。
2. AI 将需求沉淀为本地 `spec-bifrost.json`。
3. 产品通过可视化预览检查需求表达。
4. 产品与开发共同评审并修改同一份需求资产。
5. 开发侧 AI 继续使用同一份结构化上下文理解需求。
6. 团队导出前端版和后端版需求文档。

需求资产仍然是产品需求，不延伸到生产代码、接口定义、数据库设计、技术架构或任务拆分。

## 当前阶段策略

当前阶段采用“推广优先、产品冻结”策略。

在收到有效外部反馈前：

- 不修改 schema、renderer、CLI、hooks 或 skills。
- 不新增组件、字段类型、命令或平台入口。
- 不自行设计新功能来推导用户需求。
- 不建设托管服务、团队账号、云端协作或遥测。
- 不以内部模拟、stars、浏览量或泛泛评价替代真实使用证据。

允许继续修改：

- `README.md`、`README.en.md` 和插件 README。
- 演示视频、截图、推广文章和社区帖子。
- GitHub Discussion、Issue 模板和其他主动反馈入口。
- 不改变产品行为的安装、试用和定位说明。

产品代码仅在以下情况允许破例修改：

- 存在安全漏洞。
- 存在经过确认且阻止用户安装或启动的严重缺陷。

## 推广方式

推广从现有 v0.4.1 和采购系统示例开始，不等待新案例或新功能。

所有内容围绕三个主题：

1. 产品和开发都在使用 AI，但两侧上下文没有联通。
2. 为什么可审查的 JSON 需求资产比直接生成代码更适合不完全信任 AI 代码的团队。
3. 现有采购系统如何完成需求沉淀、原型预览和前后端需求文档导出。

### 中文渠道

从 V2EX、即刻、掘金、知乎和产品经理社区中选择已有账号基础最好的两个渠道。避免同时维护所有平台。

### 英文渠道

从 GitHub、Hacker News、Reddit 和 Dev.to 中选择两个渠道。英文内容与中文内容表达同一事实，但按社区语境调整标题和叙事。

### 内容节奏

在每周 5–10 小时投入下：

- 50% 用于发布和分发中英文内容。
- 30% 用于回复问题、观察讨论和整理反馈。
- 20% 用于改进 README、演示和试用说明。

同一个核心内容应复用于中英文 README、长文、短帖和演示，避免为每个渠道单独生产一套内容。

## 自助试用路径

推广材料应引导用户完成以下最短路径：

1. 理解产品与开发 AI 上下文断裂的问题。
2. 观看现有工作流演示。
3. 安装插件并运行采购系统示例。
4. 在自己的新项目中生成第一版 `spec-bifrost.json`。
5. 完成预览、产品评审、开发评审和文档导出。
6. 通过公开入口提交反馈。

README 和演示材料可以持续优化这条路径，但在没有外部证据时不得借机改变产品行为。

## 有效反馈定义

有效反馈必须来自实际尝试过 Spec Bifrost 的外部用户，并至少说明：

- 所在团队或角色组合。
- 正在规划的 B 端系统场景。
- 实际完成到工作流的哪个环节。
- 遇到的具体阻塞，或已经获得的具体价值。

以下内容不单独视为有效反馈：

- stars、收藏、转发或浏览量。
- 未实际试用的功能建议。
- “项目不错”等泛泛评价。
- 仅根据 README 提出的抽象意见。

反馈记录至少按以下阶段分类：

- 理解价值。
- 完成安装。
- 运行示例。
- 创建自己的 spec。
- 完成产品评审。
- 完成开发评审。
- 完成前后端文档导出。
- 在第二个项目中继续使用。

## 产品代码解冻条件

满足以下任一条件后，才评估恢复产品开发：

1. 收到可复现的严重缺陷反馈。
2. 至少三个外部用户反馈同一个工作流阻塞。
3. 有外部团队完成完整闭环，并提出与核心协作价值一致的明确下一步需求。

解冻不代表立即实现。每项候选变更仍需判断：

- 是否服务于产品与开发共享需求资产的核心价值。
- 是否阻断多个团队完成闭环。
- 是否可以通过文档或现有能力解决。
- 是否保持需求原型和需求文档的产品边界。

## 阶段目标与复盘

首阶段目标是获得三条有效外部反馈，并争取至少一个团队完成完整闭环。

完整闭环包括：

- 从零描述一个真实 B 端系统。
- 生成并修改 `spec-bifrost.json`。
- 完成原型预览。
- 产品与开发共同评审。
- 导出前端版和后端版需求文档。

每两周复盘一次：

- 有访问但无试用：检查定位、安装路径和演示是否清楚。
- 有试用但无反馈：检查反馈入口和询问方式。
- 有反馈但无闭环：记录阻塞，等待达到代码解冻条件。
- 用户只关注原型生成：调整价值叙事，强化共享需求资产。
- 用户认可协作价值：继续寻找重复证据，不立即扩展功能。

若连续 8–12 周仍未获得有效外部反馈，应停止增加推广材料，重新评估渠道、目标用户是否可触达，以及核心问题是否足够强。此时仍不应通过新增功能制造进展感。

## 成功标准

当前阶段成功需要同时具备市场证据和协作证据：

- 至少三条有效外部反馈。
- 至少一个外部团队完成完整闭环。
- 至少两个外部用户明确指出共享需求资产减少了重复转述、上下文丢失或语义漂移中的至少一项。
- 出现一个满足产品代码解冻条件的重复问题或明确需求，或者证据表明当前产品已足够完成目标工作流。

## 风险与控制

### 曝光被误认为采用

不以 stars、阅读量或转发量决定产品开发，仅用它们判断渠道触达。

### 用户把产品理解为原型生成器

README、文章和演示必须从产品与开发上下文断裂切入，而不是从组件数量或视觉效果切入。

### 双语运营消耗过大

中英文保持事实同步，但不要求每个渠道都有独立内容。优先复用同一核心材料。

### 个别功能建议打乱方向

单个用户的功能建议只记录，不触发开发。只有严重缺陷、三个重复阻塞或完整闭环后的明确需求可以进入解冻评估。

### 冻结代码被误解为停止维护

安全漏洞和确认阻止安装的严重缺陷仍可修复；使用问题继续响应，文档和推广材料继续迭代。

## 结论

Spec Bifrost 下一阶段不需要更多内部设想，而需要更多外部证据。团队应使用当前稳定版本立即推广，在没有用户反馈前冻结产品代码，并以真实试用过程决定后续开发方向。
